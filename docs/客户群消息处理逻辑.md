# 客户群消息处理逻辑

> 本文档描述客户群收到微信消息后，系统从入口到 AI 处理、工具调用、订单创建的完整链路。

---

## 一、总体架构

```
微信消息回调 → ingest_runtime_message() → 消息分流
                                            ├── 发货群 → 发货扫码流程（不走 AI 对话）
                                            ├── 客户群 → AI 对话流程（本文重点）
                                            └── 其他群 → 仅记录日志，不处理
```

**关键文件：**
- `wechat_runtime_compat.py` — 消息入口、分流、并发控制
- `ai_chat_service.py` — AI 对话核心（System Prompt、批次窗口、工具调用、对话历史管理）
- `ai_circuit_breaker.py` — AI 熔断器（连续失败暂停）

---

## 二、消息入口与分流

### 2.1 入口函数

```
ingest_runtime_message(db, payload, source, instance_id, wxid)
```

**执行顺序：**

1. **Payload 标准化** — `normalize_runtime_payload()` 统一格式
2. **实例 ID 解析** — 从参数 / payload / 数据库 wxid 映射中解析出 `instance_id`
3. **消息日志入库** — `record_message_log()` 写入 `message_logs` 表
4. **撤回检测** — 如果 `type=11123`，标记原消息为已撤回，自动作废关联的待审核订单，并异步通知 AI
5. **媒体归档** — 图片/文件消息异步下载到 OSS（`download_and_archive_background`）
6. **员工识别** — 查 `wechat_employee_accounts` 表判断发送者是否为员工
7. **群类型分流**：
   - `resolve_shipping_room()` → 命中发货群 → 走发货扫码流程，**不进入客户群 AI**
   - `resolve_customer_by_room()` → 命中客户群 → 走 AI 对话流程
   - 两者都未命中 → 仅记录日志

### 2.2 客户群消息过滤

进入客户群分支后，以下消息会被**跳过**，不送 AI：
- **非 Excel 文件**（`.xlsx`/`.xls` 以外的文件类型）

以下消息会**正常送入** AI：
- 文本消息（客户 + 员工 + 机器人自己）
- 图片消息
- Excel 文件
- 机器人自己发的消息（仅作上下文，AI 不当作报货处理）

## 三、并发控制

| 机制 | 说明 |
|------|------|
| **全局信号量** `_ai_semaphore` | 最多同时 **6 个群** 的 AI 对话并行处理 |
| **群级锁** `_room_locks[room_id]` | 同一个群的消息**串行处理**，防止对话历史竞争 |

执行链：
```
asyncio.create_task(_send_msg_to_ai(...))
  └── async with room_lock:          # 同群串行
        └── async with ai_semaphore: # 全局最多 6 并发
              └── process_customer_group_message(...)
```

## 四、AI 对话核心流程

### 4.1 `process_customer_group_message()` — 消息预处理

每条消息进入后依次执行：

#### 步骤 0：CDN 附件下载（图片/文件缺 base64 时）
- 从企微 CDN 下载附件，最多 **4 次重试**（首选模式×2 + 备用模式×2）
- 每次重试间隔 **1 秒**
- API 超时 **60 秒**
- 全部失败后向通知群发送告警

#### 步骤 0.5：图片方向矫正
- 调用 AI（vision_model）判断图片是否需要旋转（0°/90°/180°/-90°）
- 如果需要旋转，自动矫正后再送入对话

#### 步骤 1：构建 user message
- **文本消息**：`[消息ID:123][发送者姓名] 消息内容`
- **图片消息**：文本前缀 + base64 图片（multimodal）
- **Excel 文件**：转为 Markdown 表格（`openpyxl` 解析，最多 3 个 Sheet、50 行、20 列）
- **机器人自身消息**：标记为 `当前实例账号发送:XXX`

#### 步骤 2：立即保存到对话历史
- 写入 `ai_chat_messages` 表（room_id + role + content）
- **注意：消息入库与 AI 调用是解耦的**，入库是实时的，AI 调用通过批次窗口延迟

#### 步骤 2.5：熔断检查
- 如果 AI 已熔断（连续 3 次 API 失败），消息仍入库但**缓冲**，不送 AI

#### 步骤 3：批次窗口（核心延迟机制）

```
消息1 → 开启批次窗口 → 等待 22 秒
消息2 → 加入批次（刷新计数）
消息3 → 加入批次
...
22 秒到期 → 加载全部对话历史 → 一次性送 AI
```

| 参数 | 值 | 说明 |
|------|------|------|
| `BATCH_WINDOW_SECONDS` | **22 秒** | 正常批次等待窗口 |
| `BACKLOG_WINDOW_SECONDS` | **90 秒** | 企微掉线恢复后的历史消息批次窗口 |

**批次窗口规则：**
- 第 1 条消息到达时创建批次，启动 22 秒延迟任务
- 后续同群消息追加到同一批次（只增加计数，不重新计时）
- 22 秒到期后，从 `ai_chat_messages` 加载完整对话历史，一次性送 AI
- 批次处理时也受群级锁 + 全局信号量约束
- 如果是企微掉线恢复的历史消息，窗口扩大到 **90 秒**

**图片/文件拆分规则（避免多图只识别第一张）：**
- 批次内已包含 ≥1 张图片/文件时，如果又收到新的图片/文件 → **立即提交旧批次送 AI**，新消息另起新批次
- 旧批次提交前等待 **3 秒**（确保最后一条消息的 CDN 下载 / 入库完成）
- 文字消息不触发拆分，仍然合并到当前批次
- 这样每张图片都能独立被 AI 处理，避免注意力只集中在第一张图

```
示例时序：
  t=0s   图片A → 创建批次1（media_count=1）
  t=3s   文字B → 加入批次1（media_count=1, 不触发拆分）
  t=8s   图片C → 批次1 已有1张图片 → 立即提交批次1 → 创建批次2（media_count=1）
  t=3s   ↳ 批次1(图片A+文字B) 等3秒后送 AI
  t=30s  批次2(图片C) 22秒窗口到期后送 AI
```

### 4.2 `_run_ai_on_history()` — 批次到期后的 AI 调用

#### 步骤 1：加载对话历史
- 从 `ai_chat_messages` 表加载最近 **80 条**消息
- 超过 5 条之前的图片消息自动省略 base64，仅保留文本描述（节省 token）

#### 步骤 2：构建运行时上下文
- **员工消息检测**：检查本批次中是否有员工发言
- **未发货追问检测**：查询 `get_room_pending_followups` 是否有待确认的未发货订单
- **掉线恢复标记**：如果是历史补推 + 员工已接手 → 设置 `suppress_actions=True`，阻止 AI 重复操作

#### 步骤 3：组装 API messages
```
[system] 静态 System Prompt + 员工名单附录
[system] 运行时指令（掉线恢复说明 / 未发货订单列表 / 员工消息摘要）
[user]   对话历史消息 1
[user]   对话历史消息 2
...
```

#### 步骤 4：调用 AI（多轮 tool-call 循环）

| 参数 | 值 |
|------|------|
| **API 超时** | **240 秒** |
| **最大 tool-call 轮数** | **8 轮**（防无限循环） |
| **最大 token** | **16384** |
| **temperature** | **0.1** |
| **tool_choice** | `auto` |

```
循环（最多 8 轮）：
  1. 调用 AI API
  2. 如果 AI 返回纯文本（无工具调用）→ 结束
  3. 如果 AI 返回 tool_calls → 逐个执行工具 → 结果追加到 messages → 继续循环
```

每轮调用结果：
- **成功** → `record_success()` 重置熔断计数
- **失败** → `record_error()` 计数 +1，连续 3 次失败触发熔断

#### 步骤 5：清理对话历史
- `_trim_history()` 保留最近 80 条，删除更早的

## 五、AI 工具列表

AI 通过 Function Calling 调用以下工具：

| 工具名 | 功能 | 关键参数 |
|--------|------|----------|
| `create_order_review` | 创建待审核订单 | `items`(款号+颜色+尺码+数量), `order_intent`(new/replace/append), `trigger_msg_log_id` |
| `query_product_catalog` | 查询本年产品目录 | `keyword`（可选，留空返回全部） |
| `query_product_details` | 查询指定货号详情（颜色/尺码/别名） | `product_no` |
| `check_existing_reviews` | 查重：审核列表中是否已有完全一致的报货记录 | `items` |
| `void_recent_review` | 作废最近的待审核订单 | `review_id`（可选）, `reason` |
| `create_modify_review` | 创建待修改审核单（改旧单的部分内容） | `modify_description`, `original_items` |
| `send_group_message` | 向群里发消息 | `message`, `at_sender` |
| `mark_followup_continue` | 标记未发货订单"继续发货" | `order_no` |
| `create_cancel_unshipped_review` | 创建"取消未发货"审核单 | `order_no`, `reason` |

### 5.1 suppress_actions 抑制机制

当检测到**企微掉线恢复的历史消息中员工已接手处理**时，以下工具会被阻止执行：
- `create_order_review`
- `create_modify_review`
- `void_recent_review`
- `send_group_message`
- `mark_followup_continue`
- `create_cancel_unshipped_review`

只允许查询类工具（`query_product_catalog`、`query_product_details`、`check_existing_reviews`）正常执行。

## 六、AI 报货识别流程（6 步）

AI 按 System Prompt 中定义的流程依次执行：

### 步骤 1：判断是否包含报货数据
- **包含**（有货号/颜色/尺码/数量等可提取数据）→ 继续步骤 2
- **不包含**（闲聊/问候/表情包/咨询类）→ 不处理，保持静默

### 步骤 2：款号匹配
- 调用 `query_product_catalog` 查询本年产品目录
- 支持：货号精确匹配、别名匹配、**尾号简写匹配**（如 "862" 匹配 "95862"）
- 只有目录中存在的款号才能下单

### 步骤 3：颜色和尺码匹配
- 调用 `query_product_details` 获取该款号的可选颜色和尺码列表
- 颜色智能匹配：俗称 → 标准名（如 "米白"→"奶油白"、"黑"→"黑色"/"奢雅黑"）

### 步骤 4：检查信息完整性
- **四要素**：款号、颜色、尺码、数量
- 缺少任意字段 → 调用 `send_group_message` @客户询问

### 步骤 5：查重（必须在创建订单前执行）
- 调用 `check_existing_reviews` 精确比对（款号+颜色+尺码+数量全部一致才算重复）
- 查询范围：同群最近 **30 天**内 `pending` / `approved` 状态的审核单，最多 **50 条**
- **不重复** → 创建订单
- **重复** → 根据上下文判断是催单（不报单）还是真要再下一单

### 步骤 6：创建订单
- 调用 `create_order_review` 创建待审核订单
- 数据结构：每个 item = 款号+颜色，sizes 数组包含该颜色下所有尺码和数量
- 支持 `order_intent`：`new`（新下单）、`replace`（替换旧单）、`append`（追加补充）
- 创建成功后通过 SSE 通知前端

## 七、订单意图判断

| 意图 | 关键词 | 处理方式 |
|------|--------|----------|
| **new** | 默认 | 直接创建待审核订单 |
| **replace** | "替换""换单""重新报""之前不要了" | `order_intent="replace"`，审核时先取消该客户所有未发货订单再下新单 |
| **append** | "追加""再加""补几件" | `order_intent="append"` |
| **更正刚发的** | "写错了""发错了""重新发" | 先 `void_recent_review` 作废，再 `create_order_review` 新建 |
| **modify** | "改成""改数量""减几件" | `create_modify_review` 创建待修改审核单 |

## 八、撤回消息处理

```
客户撤回消息 → type=11123 回调
  1. mark_recalled() 标记原消息
  2. void_reviews_for_recalled_message() 自动作废该消息触发的所有 pending 审核单
  3. 异步通知 AI（_send_recall_to_ai）：
     "[系统通知] XXX 撤回了一条消息。被撤回的原始内容：..."
  4. AI 收到后保持静默，不回复、不调用工具
```

---

## 九、未发货追问处理

系统会对未全部发货的订单发追问消息（第 3 天 / 第 5 天），客户回复后 AI 判断意图：

| 客户回复 | AI 动作 | 工具 |
|----------|---------|------|
| "继续发""等一下发" | 标记继续发货，第 5 天再追问 | `mark_followup_continue` |
| "取消""不要了" | 创建取消审核单 | `create_cancel_unshipped_review` |
| 无法判断对应哪张单 | 群里追问具体订单号 | `send_group_message` |

**注意：** 这两种情况 AI 调用工具后**不再发群消息**（系统自动推送通知）。

## 十、AI 熔断机制

| 参数 | 值 |
|------|------|
| 连续错误阈值 | **3 次** |
| 触发后效果 | AI 暂停，新消息仍入库但缓冲不调用 |
| 恢复方式 | 手动恢复 |
| 缓冲区 | 记录熔断期间所有消息（room_id, sender, content_preview） |

|------|------|

## 十二、System Prompt 结构

```
静态 Prompt
  ├── 一、职责
  ├── 二、消息格式（消息ID标注、员工区分、撤回通知、机器人自身消息）
  ├── 三、报货识别流程（6 步）
  ├── 四、名称映射与别名系统
  ├── 五、图片和表格解析注意事项
  ├── 六、订单意图判断（new/replace/append/modify/撤回）
  ├── 七、回复规范（何时回复、何时静默）
  ├── 八、语气和风格（口语化、简短、自然）
  └── 附录：员工名单（动态注入，缓存 5 分钟）

运行时指令（每次批次调用时动态追加）
  ├── 掉线恢复说明（如有）
  ├── 员工消息摘要（如有）
  ├── 当前群待确认的未发货订单列表（如有）
  └── 最后一条消息是否为机器人自身发送（如有）
```

## 十三、关键时间参数汇总

| 参数 | 值 | 位置 |
|------|------|------|
| 批次窗口（正常） | **22 秒** | `BATCH_WINDOW_SECONDS` |

| 查重范围 | **30 天** | `check_existing_reviews` SQL |
| AI 熔断阈值 | **连续 3 次** | `MAX_CONSECUTIVE_ERRORS` |
| 全局 AI 并发 | **6 个群** | `_AI_MAX_CONCURRENCY` |

## 十四、完整时序图

```
客户在群里发消息
  │
  ▼
ingest_runtime_message()
  │
  ├── record_message_log()                          ← 写入 message_logs
  ├── 撤回检测 (type=11123?)                         ← 如是则标记+作废+通知AI
  ├── download_and_archive_background()              ← 图片/文件异步归档
  ├── resolve_shipping_room() / resolve_customer_by_room()  ← 分流
  │
  ▼ [客户群]
asyncio.create_task(_send_msg_to_ai(...))
  │
  ▼
_send_msg_to_ai()
  ├── room_lock (同群串行)
  ├── ai_semaphore (全局≤6并发)
  │
  ▼
process_customer_group_message()
  │
  ├── CDN 下载附件 (如缺 base64)                      ← 最多重试 4 次
  ├── 图片方向矫正                                     ← AI 判断 + 旋转
  ├── 构建 user message content
  ├── _save_message() → ai_chat_messages               ← 立即入库
  ├── 熔断检查                                         ← 如已熔断则缓冲
  │
  ▼ [批次窗口]
  首条消息 → 创建批次 → _batch_delayed_ai_call()
  后续消息 → 加入批次（不重新计时）
            │
            ▼ (等待 22 秒 / 90 秒)
  _batch_delayed_ai_call()
    ├── room_lock + ai_semaphore
    │
    ▼
  _run_ai_on_history()
    ├── _load_history() → 加载最近 80 条对话
    ├── _build_system_prompt() → 静态 Prompt + 员工名单
    ├── _build_runtime_instruction() → 运行时指令
    │
    ▼ [AI 多轮循环, 最多 8 轮]
    _call_chat_api() → AI API (timeout=240s)
      ├── 返回纯文本 → 结束
      └── 返回 tool_calls → _execute_tool()
            ├── create_order_review      → 写 downstream_order_reviews
            ├── query_product_catalog    → 查本年产品目录
            ├── query_product_details    → 查货号详情
            ├── check_existing_reviews   → 查重
            ├── void_recent_review       → 作废审核单
            ├── create_modify_review     → 创建修改审核单
            ├── send_group_message       → 发群消息
            ├── mark_followup_continue   → 标记继续发货
            └── create_cancel_unshipped_review → 创建取消审核单
          结果追加到 messages → 继续下一轮
    │
    ▼
  _trim_history() → 清理超过 80 条的旧消息
```
